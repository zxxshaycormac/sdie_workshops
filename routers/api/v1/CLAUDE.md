# `routers/api/v1/` — Design Conventions

`routers/api/v1/` exposes the REST API (mounted at `/api/v1/` via `routers/api/v1/api.go:Routes`): it binds JSON request bodies, enforces auth/permission through middleware declared at route registration, dispatches side-effecting work to `services/`, and serialises responses (mostly) through `services/convert`. This file goes deeper than `design.md` on the API-specific rules; the cross-cutting rules (architecture, naming, errors, context, logging, i18n, testing, security) and the browser-router rules (`routers/web/CLAUDE.md`) are not repeated here.

---

## 1. Handler Signature — `func Xxx(ctx *context.APIContext)`

**Rule**: Every exported API handler takes a single `ctx *context.APIContext` parameter, where `context` is aliased as `code.gitea.io/gitea/services/context`. Do not use the browser-facing `*context.Context` and do not invent a router-local type.
**Why**: `APIContext` (defined at `services/context/api.go:27`) carries the API-specific response helpers (`Error`, `NotFound`, `SetLinkHeader`) and the same `ctx.Repo`, `ctx.Doer`, `ctx.ContextUser` population that the web path uses. The middleware chain (`context.APIContexter` at `routers/api/v1/api.go:869` → `apiAuth` at `routers/api/v1/api.go:755` → `verifyAuthWithOptions` at `routers/api/v1/api.go:769`) populates it before the handler runs.
**Frequency**: universal. 483 functions across `routers/api/v1/` (non-test) match `func ... *context.APIContext)` (verified `grep -rn "func.*\*context.APIContext)" routers/api/v1/ --include="*.go" | grep -v "_test.go" | wc -l` = 483). Sample handlers: `routers/api/v1/repo/repo.go:43` (`Search`), `routers/api/v1/user/user.go:19` (`Search`).
**Exceptions**: Helper functions inside a handler file may take additional typed parameters (e.g. `CreateUserRepo` at `routers/api/v1/repo/repo.go:242` takes `owner *user_model.User` and `opt api.CreateRepoOption`) but the route-registered entry point is always `*context.APIContext`.

## 2. Swagger Annotation — `swagger:operation` Block, Regenerate After Every Change

**Rule**: Every API handler carries a `// swagger:operation <METHOD> <path> <tag> <operationID>` comment block immediately before its `func` declaration, with `summary:`, `parameters:`, and `responses:` sections. Request/response bodies are referenced as `"$ref": "#/definitions/XxxOption"` (declared in `modules/structs`) and `"$ref": "#/responses/XxxName"` (declared with `// swagger:response XxxName` in `routers/api/v1/swagger/*.go`). Run `make generate-swagger` after any annotation change.
**Why**: Gitea uses go-swagger with the `swagger:operation` (YAML-style) format, not the swag v2 `@Summary`/`@Router` format. The generated `templates/swagger/v1_json.tmpl` is consumed by the `/api/v1/swagger.json` endpoint and external tooling; failing to regenerate leaves the published spec out of sync with the code.
**Frequency**: universal. 406 `swagger:operation` annotations across `routers/api/v1/` (verified `grep -rn "swagger:operation" routers/api/v1/ --include="*.go" | wc -l` = 406). Example block: `routers/api/v1/repo/repo.go:291-311` annotates the `POST /user/repos` handler with `CreateRepoOption` body and `201`/`400`/`409`/`422` responses. Response templates live in `routers/api/v1/swagger/*.go` (e.g. `routers/api/v1/swagger/org.go:11` declares `// swagger:response Organization`); 118 `swagger:response` declarations across the package.
**Exceptions**: Internal helpers not registered as routes (e.g. `CreateUserRepo` at `routers/api/v1/repo/repo.go:242`) are not annotated. Non-API packages that need their types in the spec put them in `modules/structs` and reference the definition, not a route annotation.

## 3. Request Binding — `bind(api.XxxOption{})` at Route Registration, `web.GetForm(ctx)` Inside the Handler

**Rule**: Structured request bodies are declared as `api.XxxOption` types in `modules/structs` and bound at route registration via the `bind(api.XxxOption{})` middleware factory (defined at `routers/api/v1/api.go:726`). Inside the handler the bound value is retrieved with `opt := web.GetForm(ctx).(*api.XxxOption)`. Ad-hoc query params use `ctx.FormString`/`ctx.FormInt`/`ctx.FormBool`/`ctx.FormTrim`.
**Why**: `bind` runs `binding.Bind(ctx.Req, theObj)` as middleware before the handler, surfacing validation failures through a `422 validationError` response (`routers/api/v1/api.go:731`); `web.SetForm` stores the typed pointer for retrieval. This is the API-side analog of the web router's `web.Bind(forms.XxxForm{})` (see `routers/web/CLAUDE.md` Section 2). Do not call `ctx.Bind(...)` — that method does not exist on `APIContext`.
**Frequency**: common. 103 `bind(...)` call sites in `routers/api/v1/api.go` (verified `grep -c "bind(" routers/api/v1/api.go`); 104 `web.GetForm(ctx)` retrievals in handlers across `routers/api/v1/` (verified `grep -rn "web.GetForm(ctx)" routers/api/v1/ --include="*.go" | wc -l`). Example route+handler pair: `routers/api/v1/api.go:1079` registers `Post(bind(api.CreateRepoOption{}), repo.Create)`; the handler at `routers/api/v1/repo/repo.go:312` opens with `opt := web.GetForm(ctx).(*api.CreateRepoOption)`.
**Exceptions**: GET-only handlers that take path/query params (`repo.GetByID`, `user.Search`) do not need a bound struct. List handlers use `utils.GetListOptions(ctx)` (`routers/api/v1/utils/page.go:13`) to parse `page`/`limit` query params.

## 4. Response — `ctx.JSON(status, body)` for Success, `ctx.Error(status, title, obj)` for Failure

**Rule**: Return success with `ctx.JSON(status, body)` where `body` is either an `api.Xxx` struct produced by `services/convert.ToXxx(...)` or a primitive. Return failure with `ctx.Error(status, title, obj)` (defined at `services/context/api.go:115`) where `title` is a short English diagnostic and `obj` is an error or message string; or `ctx.NotFound(...)` (`services/context/api.go:246`) for missing resources. Never write the response body manually.
**Why**: `ctx.Error` serialises an `APIError{Message, URL}` JSON body consistently (`services/context/api.go:131-134`), logs at `Error` level when status is 500, and hides internal messages from non-admin callers in production (`services/context/api.go:123-128`). `services/convert` is the single wire-format serializer shared with webhook payloads (see `services/CLAUDE.md` Section 8), so routing all responses through it keeps the API and webhook shapes identical.
**Frequency**: universal. 286 `ctx.JSON(...)` call sites and 1,080 `ctx.Error(...)` call sites across `routers/api/v1/` non-test files (verified `grep -rn "ctx.JSON\|c.JSON" routers/api/v1/ --include="*.go" | grep -v "_test.go" | wc -l` and `grep -rn "ctx.Error\|c.Error" routers/api/v1/ --include="*.go" | grep -v "_test.go" | wc -l`). Example success path: `routers/api/v1/repo/repo.go:286` returns `ctx.JSON(http.StatusCreated, convert.ToRepo(ctx, repo, ...))`. Example error path: `routers/api/v1/repo/commits.go:68` returns `ctx.Error(http.StatusUnprocessableEntity, "no valid ref or sha", ...)`.
**Exceptions**: A handful of handlers return ad-hoc `map[string]any` bodies when the response shape is one-off (`routers/api/v1/repo/repo.go:393`); prefer a named struct in `modules/structs` for anything reused. `ctx.NotFound()` with no args returns the localised `error.not_found` message (`services/context/api.go:247`).

## 5. Status Code Conventions — 400/401/403/404/409/422/500

**Rule**: Use the established status codes consistently: `400 Bad Request` for malformed input that passed binding but failed semantic validation; `401 Unauthorized` for missing/invalid auth; `403 Forbidden` for insufficient permission or scope; `404 Not Found` for missing resources or feature-not-enabled; `409 Conflict` for duplicate/already-exists; `422 Unprocessable Entity` for binding/validation failure; `500 Internal Server Error` for unexpected server-side errors (logged by `ctx.Error`). Success codes: `200 OK` for reads/updates, `201 Created` for new resources, `204 No Content` for deletions.
**Why**: Clients branch on status codes; mixing 400 and 422 for validation, or 403 and 404 for permission gating (which leaks existence), forces every client to special-case Gitea. The middleware factories (`reqToken`, `reqAdmin`, `reqRepoReader`, `reqOwner`) emit the canonical 401/403 themselves so handlers do not have to.
**Frequency**: common. Verified counts across `routers/api/v1/` (non-test): `StatusOK` 218, `StatusCreated` 55, `StatusNoContent` 104, `StatusBadRequest` 84, `StatusUnauthorized` 5, `StatusForbidden` 121, `StatusNotFound` 47, `StatusConflict` 33, `StatusUnprocessableEntity` 152, `StatusInternalServerError` 650 (verified `grep -rn "<code>" routers/api/v1/ --include="*.go" | grep -v "_test.go" | wc -l` per code). Middleware emits the auth codes (e.g. `routers/api/v1/api.go:353` `401 reqToken`, `routers/api/v1/api.go:419` `403 reqAdmin`, `routers/api/v1/api.go:731` `422 validationError` from `bind`); handlers emit 404/409/422/500 inline. Example 409 path: `routers/api/v1/repo/release.go:252` `ctx.Error(http.StatusConflict, "ReleaseAlreadyExist", err)`.
**Exceptions**: `StatusUnauthorized` (401) is rare in handlers — 4 of the 5 occurrences are middleware in `routers/api/v1/api.go:353,360,379,759`; the lone handler-side call is `routers/api/v1/repo/mirror.go:408` — because auth failure is enforced by `reqToken`/`apiAuth` middleware before the handler runs. Prefer 403 for "authenticated but not allowed"; reserve 401 for "no/invalid token" emitted by middleware.

## 6. Permission Checks — Middleware at Route Registration, Never Assume

**Rule**: Authentication (`reqToken` at `routers/api/v1/api.go:343`), authorisation (`reqOwner:396`, `reqAdmin:416`, `reqRepoReader(unit.TypeXxx):445`, `reqAnyRepoReader:455`, `reqOrgMembership:534`), repo assignment (`repoAssignment()` at `routers/api/v1/api.go:137`), user assignment (`context.UserAssignmentAPI()` at `services/context/user.go:55`), and package assignment (`context.PackageAssignmentAPI()` at `services/context/package.go:53`) are attached as middleware at route registration in `routers/api/v1/api.go`. Do not write inline `if !ctx.IsSigned` checks at handler entry; the middleware cannot be forgotten when routes are added.
**Why**: `repoAssignment()` populates `ctx.Repo.Repository` and `ctx.Repo.Permission` (`routers/api/v1/api.go:167,189,215`) before any `reqRepoReader`/`reqOwner` check runs, so the permission middleware can read the populated fields. Inline checks get forgotten; the middleware chain is the contract. The token-scope limiter (`tokenRequiresScopes` at `routers/api/v1/api.go:296`) and the public-only guard (`checkTokenPublicOnly` at `routers/api/v1/api.go:238`) compose the same way.
**Frequency**: universal. 5 `repoAssignment()` call sites (plus 1 function declaration at line 137) and 8 `context.UserAssignmentAPI()` call sites in `routers/api/v1/api.go`; every repo-scoped route applies `reqRepoReader`/`reqOwner`/`reqAdmin` after `repoAssignment()`. Example: `routers/api/v1/api.go:1141` registers `Patch(reqToken(), reqAdmin(), bind(api.EditRepoOption{}), repo.Edit)` — the middleware runs before `bind` and before the handler. Coarse access is enforced by middleware; fine-grained per-object checks (e.g. "can this user edit this specific comment?") still happen in the handler.
**Exceptions**: Handlers that need object-level permission the middleware cannot know about do the check inline after middleware passes — this is correct layered enforcement, not a violation. The middleware chain order matters: `repoAssignment()` before `reqRepoReader`/`reqOwner` because the latter read `ctx.Repo.Permission`.

## 7. Boundary — Writes Through `services/`, Reads May Touch `models/` Directly

**Rule**: New handlers MUST route side-effecting writes through `services/` packages (`repo_service`, `issue_service`, `pull_service`, `actions_service`, etc.) and MUST NOT open DB transactions themselves. Read-only reference-data lookups (`repo_model.GetRepositoryByID`, `user_model.GetUserByName`, enumeration queries) are the established pattern and may be called directly. Wire-format transformation goes through `services/convert.ToXxx(ctx, ...)` (`services/convert/repository.go:21`, `services/convert/issue.go:21`, `services/convert/user.go:16`), never inline.
**Why**: A workflow (create repo + init git + seed labels + watch) must atomically succeed or roll back and must fire webhooks/notifications/mail/indexing consistently across the web UI, API, and CLI. If the handler opened the transaction, every call site would have to remember to commit, and the side-effect fan-out would get skipped on the CLI path. `services/convert` is shared with `services/webhook` so API responses and webhook payloads stay shape-identical.
**Frequency**: common for both. 105 files under `routers/api/v1/` import at least one `services/` package and 77 import at least one `models/` package (verified `grep -rln "code.gitea.io/gitea/services/" routers/api/v1/ --include="*.go" | wc -l` and `grep -rln "code.gitea.io/gitea/models/" routers/api/v1/ --include="*.go" | wc -l`). Example write path: `routers/api/v1/repo/repo.go:253` calls `repo_service.CreateRepository(ctx, ctx.Doer, owner, repo_service.CreateRepoOptions{...})`. Example read path: `routers/api/v1/repo/repo.go:206` calls `repo_model.SearchRepository(ctx, opts)` directly. 213 `convert.ToXxx` call sites across `routers/api/v1/` (verified `grep -rn "convert\." routers/api/v1/ --include="*.go" | wc -l`).
**Exceptions**: Reference-data lookups (assignees, milestones, labels, units, permission enums) are accepted reads; matching existing file style when extending them is fine. New write paths must go through `services/` — opening a transaction in a handler is a violation.

## 8. API Version Compatibility — Add Fields, Never Remove or Rename

**Rule**: The `/api/v1/` response shapes are contractual: existing JSON fields MUST keep their name and type across releases. Add new optional fields (with `omitempty` tags where appropriate) rather than renaming or removing existing ones. New endpoints and new optional request fields are safe; renamed/removed fields or newly-required fields are breaking changes that require a `/api/v2/` migration, not a patch release.
**Why**: External integrations (CI bots, mirrors, dashboards) parse the JSON by field name; renaming `default_branch` to `defaultBranch` or making `private` required breaks every client at once. Gitea's 1.22.x branch is backport-focused (see root `CLAUDE.md`), so additive changes are the only safe ones. The `api.Xxx` structs in `modules/structs` are the wire contract — change them carefully and regenerate Swagger (`make generate-swagger`).
**Frequency**: aspirational. The `modules/structs/*.go` types (`api.Repository`, `api.Issue`, `api.User`, etc.) evolve additively; the deprecation notices on `Token` and `AccessToken` query-param auth in `routers/api/v1/api.go:38,43` show the established pattern of marking removals with a deprecation window before the next major version. No verified grep — this rule is a contract review gate, not a code-shape pattern.
**Exceptions**: Internal-only fields (those consumed by Gitea itself, not documented in the spec) may be refactored. Security-sensitive fields (e.g. tokens, internal IDs leaked by accident) may be removed in a minor release with a release note; this is rare and must be called out in the changelog.

## 9. List Endpoints — Pagination via `utils.GetListOptions(ctx)` and `ctx.SetLinkHeader`

**Rule**: List endpoints parse `page` and `limit` query params via `utils.GetListOptions(ctx)` (defined at `routers/api/v1/utils/page.go:13`) and emit a `Link` header with `first`/`prev`/`next`/`last` URLs via `ctx.SetLinkHeader(total, pageSize)` (defined at `services/context/api.go:203`) before returning the JSON array. Default page size and max page size are enforced inside `GetListOptions`.
**Why**: Gitea API clients (and the Gitea SDK) follow the `Link` header to walk pages; omitting it forces clients to guess whether more results exist. Centralising the parsing in `utils.GetListOptions` keeps the query-param contract (`page`, `limit`) identical across every list endpoint and bounds the page size uniformly.
**Frequency**: common. 71 `GetListOptions(ctx)` call sites and 23 `ctx.SetLinkHeader(...)` call sites across `routers/api/v1/` (verified `grep -rn "GetListOptions(ctx)" routers/api/v1/ --include="*.go" | wc -l` and `grep -rn "SetLinkHeader" routers/api/v1/ --include="*.go" | wc -l`). Example list handler: `routers/api/v1/user/user.go:56` opens `listOptions := utils.GetListOptions(ctx)`; `routers/api/v1/admin/org.go:120` ends with `ctx.SetLinkHeader(int(maxResults), listOptions.PageSize)` before the JSON response.
**Exceptions**: Single-resource endpoints (`GET /repos/{owner}/{repo}`) do not paginate. Search endpoints that return a count alongside results (`GET /repos/search`) may include the count in the body rather than a Link header — match the existing endpoint's shape when adding a new search route.
