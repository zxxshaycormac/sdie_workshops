## 练习任务

### 产品需求（来自 Issue）

> **Issue [#31998](https://github.com/go-gitea/gitea/issues/31998)：仓库 Tags 页面没有搜索功能**
>
> 在 Gitea 的仓库标签（Tags）页面，当仓库有大量标签时，用户无法快速找到特定标签。而仓库的 Branches 和 Commits 页面已经有搜索/过滤功能，Tags 页面缺少一致的用户体验。
>
> **期望行为**：用户可以在 `/{org}/{repo}/tags` 页面通过关键词搜索标签名称，与已有的 Branches/Commits 搜索模式保持一致。

### 学员引导路径

**讲师不直接展示答案 PR，而是通过 SDIE 流程引导学员自己发现方案：**

#### (S)pec 阶段 — 用 brainstorming 澄清需求

学员应通过 brainstorming 回答以下问题：

- **目标**：用户能在 Tags 页面按关键词过滤标签——还隐含什么？
- **非目标**：是否需要支持正则搜索？是否需要按日期/版本号排序过滤？
- **参考模式**：Branches 和 Commits 页面的搜索是怎么实现的？找到它们的代码路径
- **影响范围**：需要改哪些层？（model / router / template / i18n）
- **验收标准**：输入关键词后只显示匹配的标签；清空关键词显示所有标签；无匹配时显示空状态提示

#### (D)esign 阶段 — 用 writing-plans 拆分任务

学员应自行探索现有 Branches/Commits 的搜索实现模式，然后设计自己的任务拆分。**不要直接告诉学员改哪些文件**——让他们通过 Explore Agent 找到参考代码，自己推断改动路径。

预期的任务粒度（供讲师参考，不直接给学员）：

1. 阅读 Branches 搜索实现，找到搜索参数传递模式
2. 在 Model 层添加按关键词过滤 Tag 的方法
3. 在 Router 层接收 `q` 参数并传递给 Model
4. 在 Template 中添加搜索输入框和空结果提示
5. 添加 i18n 文案
6. 编写测试验证过滤逻辑

#### (I)mpl 阶段 — 用 TDD 执行

先写一个失败测试（验证关键词过滤），再实现过滤逻辑，最后重构。

#### (E)val 阶段 — 用 verification-before-completion 验证

运行测试、启动本地 Gitea 实例、手动验证搜索功能。

### 技术上下文（来自 W0）

学员已通过 W0 了解：
- Gitea 是 Go + Vue 的 Git 托管平台
- 代码结构：`models/`（数据层）→ `routers/`（路由层）→ `templates/`（模板层）
- Tags 相关代码在 `models/repo/release.go` 和 `routers/web/repo/release.go`

### SDIE 映射

```
(S)pec: brainstorming → Proposal → Domain Model → BDD
  输入：Issue #31998 + W0 产出的 specs/ + CLAUDE.md
  产出：proposal.md（含非目标）、BDD 验收标准

(D)esign: writing-plans → 探索参考模式 + tasks.md
  输入：通过 Explore Agent 找到 Branches/Commits 搜索的实现
  产出：tasks.md（每个任务 2-5 分钟粒度）

(I)mpl: executing-plans + TDD → Red-Green-Refactor
  产出：可验证的代码变更 + 对应测试

(E)val: verification-before-completion → 测试 + 手动验证
  产出：验证通过报告
```

### 关键约束

- 必须先完成 Spec 再开始实现（禁止跳步）
- **不允许直接搜索或阅读 PR #32045**——靠自己探索 Branches/Commits 的模式来推导方案
- 每个任务控制在 2-5 分钟粒度
- TDD 纪律：先写失败测试，再写最小实现，最后重构

## 概念回顾要点

### SDIE 四阶段一句话总结

1. **(S)pecification**：从模糊到规约——确认做什么、不做什么
2. **(D)esign**：从规约到契约——确认怎么做、怎么拆
3. **(I)mplementation**：从契约到代码——按约束执行、用测试守门
4. **(E)valuation**：从代码到确认——验证做对了、也做了对的事

### Agentic Engineering 核心认知

- 产出质量 = 上下文质量 × 任务粒度 × 验证闭环
- L4 级别：开发者委派目标，Agent 自行决定实现方式
- 前提：CLAUDE.md + Harness + 结构化需求

### 三位一体

- 提示词告诉 LLM 做什么
- 上下文告诉 LLM 需要知道什么
- Harness 确保 LLM 做对了

## 讲师 Notes

### 开场建议

- 回顾 W0："昨天我们画了地图——建立了系统的心智模型"
- 问："有了地图，现在要加一条新路，第一步做什么？" → 引出 SDIE 的 Spec 阶段
- 强调：W0 产出的 CLAUDE.md 和 specs/ 就是今天的"已有上下文"
- 问："谁遇到过 AI 越改越乱的情况？" → 引出 SDIE 的必要性
- 点明今天的目标：从"凭感觉用 AI"升级到"有方法地用 AI"

### 实操 1 关键引导

- 确保 brainstorming 不跳过——学员倾向直接开始写代码
- 提醒：先去探索 Branches/Commits 的搜索是怎么实现的（用 Explore Agent），再设计自己的方案
- 提醒：Proposal 的"非目标"比"目标"更重要
- 检查 tasks.md 是否拆到 2-5 分钟粒度
- **如果学员问"应该改哪些文件"**——不要直接回答，引导他们用 Explore Agent 搜索 `q` 参数在 Branches 页面的传递路径

### 实操 2 关键引导

- TDD 纪律：RED 阶段不允许写实现代码
- 核心挑战：学员需要自己发现 Model 层的过滤方法应该怎么写（参考 Branches 的模式）
- 如果 Agent 连续失败 2-3 次，引导学员 Esc 重来
- 提醒 50% 上下文时主动 /compact

### 回顾要点

- 让学员用自己的话描述 SDIE 四阶段分别做了什么
- 引出："我们今天用 CLAUDE.md 做了推理型前馈，但模型可能忽略——明天我们加计算型反馈"
- 预告 W2：Harness 2x2 矩阵 + Bug 修复
