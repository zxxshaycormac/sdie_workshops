## 逆向工程三步法

### Step 1：快速扫描——模块职责概览

**目的**：建立对系统的宏观认知，不深入实现。

**执行方式**：使用 Explore Agent（不在主会话中做）。

```text
分析以下遗留代码目录，生成模块职责概览。

## 分析要求
1. 对每个文件/目录，用一句话描述其职责
2. 标记"核心入口文件"、"数据模型文件"、"外部集成点"
3. 初步判断系统的整体架构模式（单体/MVC/分层/微服务）

## 输出格式
| 文件/目录 | 推测职责 | 分类 | 置信度（高/中/低） |
```

**原则**：
- 只看结构和命名，不看实现
- 所有推测内容标注置信度
- 广度扫描交给 Explore Agent，保护主会话上下文

**每完成一个侦察任务后 `/compact`**。

**MECE 检查点**：

```text
请用 MECE 原则检查以下模块职责概览：
1. 【相互独立】是否有两个模块承担了重叠的职责？如果有，标注重叠部分
2. 【完全穷尽】是否有文件/目录没有被任何模块覆盖？列出遗漏项
3. 给出修正建议
```

| MECE 维度 | 逆向理解中的含义 | 常见违背 |
|---|---|---|
| **Mutually Exclusive** | 每个模块有清晰独立的职责边界 | 两个模块都处理"用户数据"，职责交叉 |
| **Collectively Exhaustive** | 目录树中所有文件都被归入某个模块 | 遗漏了 utils/、middleware/ 等辅助目录 |

### Step 2：深度分析——提取行为规格

**目的**：理解核心模块的行为——输入、输出、副作用、异常。

**执行方式**：在主会话中逐模块分析。

```text
对以下核心模块进行深度行为分析，提取行为规格。

## 分析要求
1. 对每个公开方法，提取：输入、输出、副作用、异常路径
2. 标记隐含假设（如"假设用户已登录""假设库存充足"）
3. 标记代码异味（上帝方法、过长参数列表、深层嵌套）
4. 识别模块间调用关系和数据流向

## 输出格式
| 方法签名 | 行为描述 | 隐含假设 | 代码异味 | 置信度 |
```

**原则**：
- 用 Read 工具读完整代码，不依赖 Explore Agent 的摘要
- 标记**隐含假设**——它比 Bug 更危险
- 分析完一个模块后保存报告，`/compact` 再进入下一个

**MECE 检查点**：

```text
请用 MECE 原则检查以下模块的行为规格：
1. 【相互独立】每个行为是否只归属一个方法？是否存在两个方法描述了同一个行为？
2. 【完全穷尽】是否覆盖了所有公开方法？是否覆盖了正常路径、边界条件和异常路径？
3. 隐含假设是否完整列举？是否有遗漏的前置条件？
4. 给出修正建议
```

| MECE 维度 | 行为提取中的含义 | 常见违背 |
|---|---|---|
| **Mutually Exclusive** | 每个行为只被一个方法覆盖，无重复描述 | 同一个校验逻辑在两个方法的行为描述中重复出现 |
| **Collectively Exhaustive** | 所有公开方法、所有异常路径都被记录 | 只记录了 Happy Path，遗漏了空值、越权、超时等异常路径 |

### Step 3：Spec 逆向生成

**目的**：将分析成果固化为 OpenSpec 格式的基线文档。

**执行方式**：基于 Step 2 的报告逆向生成。

```text
基于模块分析报告和行为规格，逆向生成 OpenSpec 格式的需求文档。

## 生成要求
1. 将行为规格转化为用户故事和验收标准
2. 将隐含假设转化为前置条件和业务规则
3. 所有推测内容标注置信度和来源
4. 不确定的行为标注"待确认"

## 关键约束
- 不编造不存在的功能
- 推测内容必须标注置信度（高/中/低）
- 保存为 specs/reversed/xxx.md
```

**原则**：
- 不编造功能——AI 有"补全"倾向，必须约束
- 低置信度部分由讲师/业务方确认
- 输出保存为 `specs/` 目录下的文档

**MECE 检查点**：

```text
请用 MECE 原则检查以下逆向生成的 Spec：
1. 【相互独立】每条需求是否描述一个独立行为？是否存在两条需求描述同一件事？
2. 【完全穷尽】Step 2 中识别的所有行为是否都有对应的 Spec 条目？
   对比行为规格报告，列出 Spec 中遗漏的行为
3. 所有"待确认"项是否已标注？低置信度内容是否已标记？
4. 给出修正建议
```

| MECE 维度 | Spec 逆向生成中的含义 | 常见违背 |
|---|---|---|
| **Mutually Exclusive** | 每条 Spec 只描述一个行为 | 同一个订单创建流程在两处 Spec 中重复描述，且描述不一致 |
| **Collectively Exhaustive** | 所有已识别行为都有对应 Spec | 遗漏了 Step 2 中标记的"隐含假设"对应的业务规则 |

### CLAUDE.md 编写指南（逆向版）

从逆向分析中提取的 CLAUDE.md 应包含：

```markdown
# CLAUDE.md

## 系统概览
- [项目名称]，[技术栈]
- 架构模式：[单体/MVC/分层/微服务]
- 核心领域：[列出 2-5 个主要业务领域]

## 关键约束
- 构建命令：[xxx]
- 测试命令：[xxx]
- 主要技术栈版本：[xxx]

## 高风险区域（来自逆向分析）
- [文件/模块 A] — [风险原因，如"上帝方法 300+ 行"]
- [文件/模块 B] — [风险原因，如"隐含假设：假设用户已登录"]

## 隐含假设清单（来自逆向分析）
- [假设 1] — 影响范围：[xxx]
- [假设 2] — 影响范围：[xxx]

## 禁止操作
- 不要引入新的全局状态
- 不要修改 [自动生成目录]
- 外部调用必须通过 [统一网关/封装层]

## 编码规范（观察自现有代码）
- [命名风格]
- [错误处理模式]
- [日志规范]
```

## 代码理解四层模型

```
┌─────────────────────────────────────────────────┐
│  Level 4：业务意图（Why）                          │
│  "这个模块为什么存在？它解决什么业务问题？"        │
│  产出：业务上下文文档                              │
├─────────────────────────────────────────────────┤
│  Level 3：架构关系（Where）                        │
│  "这个模块在系统中的位置？它依赖谁？谁依赖它？"    │
│  产出：依赖图 + 领域清单                          │
├─────────────────────────────────────────────────┤
│  Level 2：行为规格（What）                         │
│  "这个模块做什么？输入什么？输出什么？边界在哪？"  │
│  产出：接口契约 + BDD 场景                        │
├─────────────────────────────────────────────────┤
│  Level 1：代码逻辑（How）                          │
│  "这个函数的具体实现逻辑是什么？"                  │
│  产出：代码注释 + 流程图                          │
└─────────────────────────────────────────────────┘
```

**最佳路径是自底向上**：代码逻辑 → 行为规格 → 架构关系 → 业务意图。
不要跳层——没有 Level 1 的理解就做 Level 3 的领域划分，只会得到错误的边界。

**W0 的覆盖范围**：主要覆盖 Level 1-2（代码逻辑 + 行为规格），Level 3-4 在后续 Workshop 中逐步深化。

## 上下文窗口管理策略

### 三层架构

```
Layer 1：持久层（~2000-5000 tokens）
  CLAUDE.md — 项目约束和关键规则
  .claude/rules/ — 领域/模块级规则

Layer 2：时效层（~3000-8000 tokens）
  当前模块的代码和行为分析

Layer 3：工作层（动态变化）
  搜索结果、中间推理
```

## 概念回顾要点

### 为什么"理解先于修改"

- 企业软件 70%+ 的投入在维护，不是新建
- 遗留系统不是"技术债"，而是组织知识以代码形式存在的唯一载体
- 改它不是修 Bug，是在没有地图的情况下做手术——先画地图

### MECE 在逆向理解中的核心作用

**MECE 不是额外的文档工作，而是逆向理解的自检思维**——每一步产出后问：有没有遗漏？有没有重叠？

逆向理解中的 MECE 失败会级联放大：

```
Step 1 模块划分不 MECE（有遗漏）
  → Step 2 遗漏的模块不会被深度分析
    → Step 3 Spec 缺失该模块的行为规格
      → W1-W4 在遗漏的模块上做修改 = 盲改
```

**三步法中每步的 MECE 自检问题**：

| 步骤 | MECE 自检问题 | 失败后果 |
|---|---|---|
| Step 1 模块划分 | 模块之间有重叠吗？有文件没被覆盖吗？ | 模块边界模糊 → 后续分析重复或遗漏 |
| Step 2 行为提取 | 每个行为只记录了一次吗？所有异常路径都覆盖了吗？ | 行为理解不完整 → 改代码时踩坑 |
| Step 3 Spec 生成 | 每条 Spec 独立吗？所有已识别行为都有 Spec 条目吗？ | Spec 有空缺 → 后续开发缺乏验证依据 |

**核心原则**：MECE 是对抗 AI "幻觉"和"补全"倾向的思维工具。不 MECE 的理解 = 有缺陷的地图 = 所有后续工作建立在不可靠的基线上。

### 逆向 vs 正向

| 维度 | Greenfield（绿地） | Brownfield（棕地） |
|---|---|---|
| Spec 来源 | 业务方提供 | 从代码中逆向提取 |
| Design | 全新设计 | 理解已有设计，补全或调整 |
| Implementation | 从零实现 | 在已有代码中安全插入 |
| Evaluation | 验证新功能 | 修改正确性 + 未修改行为等价性 |

### Explore Agent 使用原则

- 广度扫描交给 Explore Agent，保护主会话
- 深度分析在主会话中做，用 Read 工具读完整代码
- 不要在主会话中做广度搜索——那会快速污染上下文窗口

## 讲师 Notes

### 开场建议

- 问："谁接过别人的代码？" → 几乎全员
- 问："第一次看的时候，花了多久才敢改第一行？" → 引出"理解先于修改"
- 今天不做任何代码修改——只理解和记录

### 实操 1 关键引导

- 三个侦察任务可以并行发给 Explore Agent：
  1. 搜索主入口点、API 路由、外部服务调用
  2. 找到所有数据库模型、Schema
  3. 搜索最复杂条件逻辑、状态机的文件
- 提醒学员：只看结构，不看实现
- **MECE 自检**：扫描完成后，用 MECE Prompt 检查模块划分——确保无重叠、无遗漏
- 每个侦察完成后 /compact

### 实操 2 关键引导

- 选择 2-3 个核心模块做深度分析（不是全部）
- 重点是标记**隐含假设**——比 Bug 更危险的定时炸弹
- **MECE 自检**：每个模块分析完后，检查——所有公开方法都覆盖了吗？异常路径遗漏了吗？
- 分析完一个模块保存报告并 /compact

### 实操 3 关键引导

- Spec 逆向生成的核心约束：**不编造功能**
- 低置信度部分标注"待确认"
- **MECE 自检**：对比 Step 2 的行为规格报告，逐条确认每个行为都有对应的 Spec 条目
- CLAUDE.md 控制在 60 行以内
- 这些产出将作为 W1-W4 的基线

### 回顾要点

- 让学员描述"代码理解四层模型"
- 盘点今天产出：CLAUDE.md + specs/
