## 练习任务

### 产品需求（来自 Issue）

> **Issue [#18664](https://github.com/go-gitea/gitea/issues/18664)：Gitea 使用的邮件库 gomail 已停止维护**
>
> Gitea 的邮件发送功能依赖 `gopkg.in/gomail.v2` 库，该库自 2016 年起不再维护。社区计划切换到维护中的替代库，但在替换之前，需要先将 gomail 依赖隔离到独立子包——这样后续替换库时只需修改子包内部，不影响上层代码。
>
> **当前问题**：`services/mailer/mailer.go` 是一个 440+ 行的大文件，混合了邮件消息构造、SMTP 客户端、sendmail 调用、认证逻辑、队列管理等多种职责。gomail 依赖散落在各处，无法独立替换。
>
> **重构目标**：将邮件发送相关代码拆分到 `services/mailer/sender/` 子包。**只移动代码，不修改逻辑。**

### 学员引导路径

**讲师不直接展示答案 PR，而是引导学员通过 MECE 分析和 PEV 循环完成安全重构：**

#### Step 1：理解现状 — 用 Explore Agent 阅读 mailer.go

学员应通过 Explore Agent 回答：
- `mailer.go` 中有哪些逻辑上独立的职责？列出每个职责及其依赖
- 哪些代码依赖 `gopkg.in/gomail.v2`？哪些不依赖？
- 现有的 `Sender` 接口是什么样的？有几种实现？

#### Step 2：MECE 拆分 — 设计子包结构

学员应基于 MECE 原则设计拆分方案：

- **Mutually Exclusive**：每个文件只包含一个职责（消息构造 / SMTP 发送 / sendmail 发送 / 认证 / 空发送器）
- **Collectively Exhaustive**：mailer.go 中所有与发送相关的代码都被迁移，只保留队列管理

学员产出一份文件结构设计：

```
services/mailer/sender/
  ├── sender.go       ← 接口定义 + 工厂函数
  ├── message.go      ← Message 结构体
  ├── smtp.go         ← SMTP 发送器
  ├── smtp_auth.go    ← SMTP 认证
  ├── sendmail.go     ← sendmail 发送器
  └── dummy.go        ← 开发模式空发送器
```

#### Step 3：PEV 循环执行 — 只移动，不改逻辑

逐文件执行 Plan-Execute-Verify：

1. **Plan**：选择一个职责（如 Message 结构体），确认移动范围
2. **Execute**：创建新文件、复制代码、调整 import 路径
3. **Verify**：`go build` 确认编译通过 + 已有测试全部通过

每个文件移动后立即验证——**不要批量移动后再验证**。

#### Step 4：最终验证

- `go build` 编译通过
- `make test-backend` 所有测试通过
- `mailer.go` 精简为队列管理代码（~60 行）
- gomail 依赖被隔离在 `sender/` 子包内

## Harness 产出

### Edit Lock Hook：保护重构边界

```bash
#!/bin/bash
# .claude/hooks/edit-lock.sh
input=$(cat)
file_path=$(echo "$input" | jq -r '.tool_input.file_path // empty')

# 重构期间：只允许修改 sender/ 子包和 mailer.go
# 禁止修改 mail_*.go 模板文件（不是本次重构目标）
LOCKED_FILES=(
  "services/mailer/mail.go"
  "services/mailer/mail_release.go"
  "services/mailer/mail_repo.go"
  "services/mailer/mail_team_invite.go"
  "services/mailer/incoming/"
  "services/mailer/token/"
)

for locked in "${LOCKED_FILES[@]}"; do
  if [[ "$file_path" == *"$locked"* ]]; then
    echo "Edit Lock：$file_path 不在本次重构范围内，禁止修改。" >&2
    exit 2
  fi
done
exit 0
```

## 概念回顾要点

### MECE 原则

- **Mutually Exclusive**：每次修改只涉及一个原子变更——一个 PR 只做一件事
- **Collectively Exhaustive**：所有需要修改的点都被识别和覆盖——依赖分析不遗漏

### 先测后改

- 在没有测试的遗留代码上重构 = 没有保护网的高空体操
- Characterization Test 记录的是"当前行为"而不是"期望行为"
- 即使当前行为看起来是 Bug 也照实记录

### PEV 循环（Plan-Execute-Verify）

```
Plan: 定义"完成"标准 + 拆分原子任务 + 设定修改边界
  ↓
Execute: 只修改目标范围内的代码，严禁"顺便优化"
  ↓
Verify: Characterization Test 全通过 + 爆炸半径检查
  ↓
通过 → 下一个原子任务 / 失败 → 回滚 + 分析原因
```

### 爆炸半径控制三层防护

| 防护层 | 机制 | 实现 |
|---|---|---|
| Edit Locks | 文件保护 | Hooks 拦截高风险文件修改 |
| 依赖分析 | 影响范围可视化 | AI 分析直接/间接/数据/配置影响 |
| Fail-Safe | 自动升级 | 超阈值停止修改，升级到人工决策 |
