## 练习任务

### 产品需求（来自 Issue）

> **Issue [#32857](https://github.com/go-gitea/gitea/issues/32857)：Actions 任务状态聚合不正确**
>
> 在 Gitea Actions 中，一个 workflow 运行包含多个 job，页面需要聚合所有 job 的状态来显示整体运行结果。但当前的状态聚合逻辑不完整——只处理了 4 种状态（Failure、Success、Waiting、Running），忽略了 Cancelled、Blocked 和 Skipped。
>
> **用户可见的问题**：
> - 所有 job 都被跳过（Skipped）时，显示"Success"而不是"Skipped"
> - 有 job 被取消（Cancelled）时，显示"Failure"而不是"Cancelled"
> - 被 Blocked 的 job 完全不可见
>
> 这是一个典型的**状态机聚合 Bug**——聚合函数没有枚举所有可能的状态组合。

### 学员引导路径

**讲师不直接展示答案 PR，而是通过 systematic-debugging 引导学员自己定位根因：**

#### (E)val 逆向启动 — 用 systematic-debugging 定位 Bug

1. **现象描述**：学员在本地 Gitea 创建一个 workflow，制造"所有 job 都 skipped"的场景，观察错误的聚合状态
2. **假设生成**：
   - 假设 A：前端渲染逻辑没有处理 cancelled/skipped 状态的图标
   - 假设 B：后端聚合函数没有覆盖所有状态类型
   - 假设 C：状态枚举定义缺失某些值
3. **逐步验证**：让学员用 Explore Agent 找到 `AggregateJobStatus` 函数，阅读现有逻辑
4. **根因确认**：学员自行发现聚合函数用布尔变量（`allDone`、`hasFailure`）无法表达所有状态组合

#### (S)pec 逆向提取 — 从 Bug 提取正确行为

学员应回答：
- 有哪些 job 状态？每种状态的含义是什么？
- 多个 job 状态组合时，聚合优先级应该如何定义？（如：全部成功 = Success，有失败 = Failure）
- 被忽略的 Cancelled、Blocked、Skipped 应该如何影响聚合结果？

#### (I)mpl 修复 — 用 TDD 循环

1. **Red**：为 `AggregateJobStatus` 编写失败测试——覆盖所有状态组合（至少包含 skipped 和 cancelled 场景）
2. **Green**：修复聚合逻辑让所有测试通过
3. **Refactor**：检查是否可以简化状态判断逻辑

#### (E)val 回归 — 验证修复

确认所有已有测试仍通过 + 新测试覆盖了所有状态组合 + 前端图标正确渲染 cancelled 状态。

## Harness 产出

### PreToolUse Hook：安全拦截

```bash
#!/bin/bash
# .claude/hooks/pre-protect.sh
input=$(cat)
file_path=$(echo "$input" | jq -r '.tool_input.file_path // empty')

# 保护高风险文件不被误改
PROTECTED_FILES=(
  "src/core/config.ts"
  "src/generated/"
  ".env"
)

for protected in "${PROTECTED_FILES[@]}"; do
  if [[ "$file_path" == *"$protected"* ]]; then
    echo "安全拦截：$file_path 是受保护的高风险文件，禁止修改" >&2
    exit 2
  fi
done
exit 0
```

### PostToolUse Hook：质量检查

```bash
#!/bin/bash
# .claude/hooks/post-lint.sh
input=$(cat)
file_path=$(echo "$input" | jq -r '.tool_input.file_path // empty')

if [[ "$file_path" == *.ts || "$file_path" == *.tsx ]]; then
  # 自动格式化
  npx prettier --write "$file_path" 2>/dev/null
  # Lint 检查
  lint_output=$(npx eslint "$file_path" 2>&1)
  if [ $? -ne 0 ]; then
    echo "ESLint 发现问题：$lint_output 请修正后继续。" >&2
    exit 2
  fi
fi
exit 0
```

### Harness 配置

```json
// .claude/settings.json
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Edit|Write",
        "command": "bash .claude/hooks/pre-protect.sh"
      }
    ],
    "PostToolUse": [
      {
        "matcher": "Edit|Write",
        "command": "bash .claude/hooks/post-lint.sh"
      }
    ]
  }
}
```

## 概念回顾要点

### Harness 2x2 矩阵

| | 前馈（引导） | 反馈（传感器） |
|---|---|---|
| **计算型** | LSP、Codemod、`.editorconfig` | Linter、类型检查、测试套件 |
| **推理型** | CLAUDE.md、Skills、系统提示词 | AI 审查 Agent、LLM-as-Judge |

**信任度排序**：计算型反馈 > 计算型前馈 > 推理型反馈 > 推理型前馈

### Agent = Model + Harness

- Model 决定能力的**上限**（你无法直接改变）
- Harness 决定输出的**下限**（你可以设计和迭代）
- 类比：模型是引擎，Harness 是方向盘 + 刹车 + 仪表盘

### 引导循环

```
观察 Agent 犯错
    → 分析错误模式（偶发 or 系统性？）
    → 系统性错误 → 在 Harness 中添加约束
        → 可以确定性检测 → 添加计算型反馈（Hook / Linter）
        → 需要语义判断 → 添加推理型反馈（审查 Agent / Skill）
```

### 开场建议

- 回顾 W1："昨天我们写了 CLAUDE.md，但模型真的每次都会遵守吗？"

### 实操 1 关键引导

- 引导学员先在本地复现 Bug：创建一个所有 job 都 skipped 的 workflow
- systematic-debugging 的核心：不猜测，用证据缩小范围
- 当学员问"聚合函数在哪"时——不要直接给路径，让他们用 Grep 搜索 `AggregateJobStatus`
- 关键洞察引导：让学员数一数当前聚合函数处理了几种状态，再数一数系统里定义了多少种状态——发现数量不匹配就是根因

### 实操 2 关键引导

- 先写暴露 Bug 的测试（Red）——重点是状态组合测试，推荐用 Go 的 table-driven test
- Hook 创建过程中，让学员测试 exit 2 的效果
- 提醒：Hook 的 stderr 消息会返回给 Agent，可以包含修正指令
- 学员应自行设计聚合优先级——没有唯一正确答案，但要能自圆其说

### 实操 3 关键引导

- 让学员故意触发 Hook（尝试修改受保护文件）
- 体验"机器强制 > Prompt 恳求"
- 引导发现：哪些规则适合放 Hook，哪些适合放 CLAUDE.md

### 回顾要点

- 让学员描述 2x2 矩阵中今天用到了哪些象限
- 引出："今天 Hook 帮我们拦截了错误操作，但重构时需要更精细的控制——明天讲 MECE 和爆炸半径"
