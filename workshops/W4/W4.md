## 练习任务

### 产品需求（来自 Issue）

> **Issue [#23112](https://github.com/go-gitea/gitea/issues/23112)：Issue 缺少时间估算功能**
>
> 在项目管理工具中（如 Jira），可以为 Issue 设置预估工时（如"3d 5h"），帮助团队评估工作量和跟踪进度。Gitea 目前只支持记录已花费的时间（Time Tracking），但没有时间估算功能。
>
> **期望行为**：
> - 用户可以为 Issue 设置时间估算（格式：`1w 3d 15h 30m`）
> - 页面上显示"已花费时间 / 预估时间"的对比
> - 时间追踪评论格式统一，支持未来国际化
> - 移除无意义的秒数显示（如"1h 30m 0s" → "1h 30m"）

### 学员引导路径

**这是一个跨多层的综合任务，学员需要综合运用四天所学：**

#### (D)esign 逆向启动 — 理解时间追踪的现有架构

学员应通过 Explore Agent 回答：
- Issue 的 `TimeTracker` 相关代码在哪里？现有的时间记录是如何存储和展示的？
- 数据库中 Issue 表有哪些时间相关字段？需要新增什么字段？
- 前端的时间显示逻辑在 `stopwatch_timetracker` 模板中——它的结构是什么？

#### (S)pec 逆向提取 — 设计时间估算的行为规格

学员应产出：
- **时间格式规范**：`1w 3d 15h 30m` 的解析规则、边界条件（负数、零、超大值）
- **BDD 场景**：设置估算 → 修改估算 → 清除估算 → 在列表中显示估算进度
- **影响范围矩阵**：models / modules / services / routers / templates / i18n 各层需要改什么

#### (I)mpl 分步执行 — MECE 拆分 + 渐进实现

学员应将任务拆分为独立可验证的子任务（示例拆分供讲师参考）：

1. 实现 `modules/util/time_str.go` 时间解析工具（独立、可先做）
2. 数据库 migration：Issue 表新增 `estimate` 字段
3. Model 层：添加估算字段的读写方法
4. Service 层：时间追踪逻辑中整合估算显示
5. Router 层：接收设置估算的请求
6. Template 层：显示估算进度条和格式化时间
7. i18n 文案

每个子任务独立可测试——可以用 subagent 并行处理无依赖的任务。

#### (E)val 综合验证

- 所有新增测试通过
- 已有时间追踪测试不被破坏
- 手动验证：设置估算 → 记录时间 → 查看进度显示

### 技术上下文

- 核心 Model：`models/issues.go`（Issue 结构体）
- 时间追踪 UI：`templates/shared/stopwatch_timetracker.tmpl`
- 时间相关工具：需新建 `modules/util/time_str.go`
- 数据库 Migration：需在 `models/migrations/` 中新增版本
- 影响约 21 个文件，但核心改动集中在 3-4 个文件

### 逆向 SDIE 映射

```

```

## Skill 创建

### 引导发现过程

在完成迁移任务后，引导学员回顾四天中反复出现的操作模式：

```
Day 1: 每次 Spec 都要 brainstorming → writing-plans → executing-plans
Day 2: 每次 Bug 修复都要 systematic-debugging → TDD → Hook 验证
Day 3: 每次重构都要 Characterization Test → MECE 拆分 → PEV 循环
Day 4: 迁移任务又重复了这些模式
```

**关键提问**："哪些操作你重复了三次以上？这些能封装成 Skill 吗？"

### Skill 创建示例

以下是一个可能的学员创建的 Skill 示例——`safe-refactor`：

```markdown
---
name: safe-refactor
description: 安全重构一个模块，确保行为等价性。先建 Characterization Test，再 MECE 拆分，最后逐步重构。
---

# Safe Refactor Skill

安全重构遗留代码模块，确保行为不改变。

## 前提条件

- 目标模块已识别
- 已有或可生成 Characterization Test

## 步骤

1. **生成 Characterization Test**
   - 为目标模块的每个公开方法生成测试
   - 记录当前行为（不猜测正确行为）
   - 确认所有测试通过

2. **MECE 拆分**
   - 将重构目标拆分为原子任务
   - 每个任务独立可测试
   - 标注风险等级和影响范围

3. **PEV 循环执行**
   - Plan: 定义完成标准（行为等价性）
   - Execute: 只修改目标范围内的代码
   - Verify: Characterization Test 全通过

4. **验证完成**
   - 所有 Characterization Test 通过
   - 无超范围修改
   - diff 已人工 Review
```

### Skill 创建 Prompt

```text
请帮我创建一个 Skill，封装以下重复操作模式：

[描述你在这四天中重复了三次以上的操作]

要求：

2. 步骤明确，每步可执行

```

## 概念回顾要点

### 引导循环

```
观察 Agent 犯错
    → 分析错误模式
    → 系统性错误 → 添加 Harness 约束
        → 计算型反馈（Hook / Linter / 测试）
        → 推理型反馈（CLAUDE.md / Skill）
    → 验证效果
    → 随 Harness 积累，Agent 自主性和可信度同步提升
```

### Skill Oriented Harness

- CLI 优先：利用成熟命令行工具（`grep`、`kubectl`、`curl`）
- Skills 封装：用 `SKILL.md` 固化工具调用路径与操作逻辑
- 低成本集成：无需额外服务，仅文件

### 渐进披露

```
第一层：常驻前缀（Always Loaded）← CLAUDE.md
  成本最低，KV-Cache 友好

第二层：按需加载（On-Demand）← Skills
  名称和描述常驻，完整内容按需展开

第三层：深度引用（Deep Reference）← 外部文档
  仅在需要时读取
```

- 用 skill-creator 创建后，现场测试是否可用
